# Specification: FEAT-014 Core Domain Constraint Baseline

**Status**: APPROVED FOR IMPLEMENTATION  
**Phase**: Phase 3 - Data Foundation & Core Domain  
**Scope**: Reusable PostgreSQL/Prisma constraint standards only

## 1. User Stories

### Story 1 - Reusable Constraint Standards

As a future domain implementer, I need approved database constraint standards so new schemas are designed consistently and do not rely on application validation alone.

Independent test:

- A constraint standards document exists.
- It classifies rules as `MUST`, `SHOULD`, or `DOMAIN-SPECIFIC DECISION`.
- Future-domain product tables are not introduced by FEAT-014.

### Story 2 - PostgreSQL-Enforced Integrity

As a QA reviewer, I need live PostgreSQL evidence that key durable invariants are protected by database constraints.

Independent test:

- PostgreSQL-backed tests verify UUID primary keys, unique constraints, composite uniqueness, foreign keys, required fields, and cascade/restrict/set-null behavior using existing approved schema or dedicated test fixtures/helpers.

### Story 3 - Safe Future Migration Baseline

As an architect, I need constraint additions to remain compatible with FEAT-002 through FEAT-013 and with FEAT-012 migration governance.

Independent test:

- Fresh migration deploy/status remains clean.
- Existing approved rows remain valid.
- No destructive or product-domain migration is introduced.

## 2. Constraint Standards

### 2.1 UUID Primary Keys

MUST:

- Persistent application records use UUID primary keys unless a future feature receives explicit Human approval for another identifier strategy.
- Externally exposed record identifiers must not be sequential integers.
- Primary keys must be generated by an approved server-side/Prisma/PostgreSQL mechanism, not trusted from public client authority unless the feature explicitly approves client-supplied idempotency semantics.

SHOULD:

- Use consistent Prisma field naming, normally `id String @id @default(uuid()) @db.Uuid` or the repository-approved equivalent.

DOMAIN-SPECIFIC DECISION:

- Whether an externally opaque ID, slug, or composite natural key is also needed.

### 2.2 Foreign Keys And Cardinality

MUST:

- Durable relationships must be represented with PostgreSQL foreign keys when the referenced record is part of the same bounded persistence model.
- Required relationships must use non-nullable foreign keys.
- Optional relationships must document why null is meaningful.
- One-to-one relationships must enforce uniqueness on the dependent side.
- Many-to-many relationships must use a join table with composite uniqueness or an equivalent database constraint.
- Every relation must define an explicit deletion policy.

SHOULD:

- Index foreign keys that are used for joins, ownership checks, or cleanup paths.

DOMAIN-SPECIFIC DECISION:

- Whether cross-module references are hard foreign keys, nullable snapshots, or immutable denormalized references. Audit/event records may intentionally avoid hard user foreign keys when approved.

### 2.3 Required Fields And `NOT NULL`

MUST:

- Required durable invariants must be enforced with database-level `NOT NULL`.
- Application validation must reject invalid payloads before persistence, but PostgreSQL remains the final integrity authority.

SHOULD:

- Avoid nullable booleans and ambiguous nullable status fields.
- Document nullable fields with their semantic meaning.

DOMAIN-SPECIFIC DECISION:

- Whether optional data is modeled as nullable columns, separate detail tables, or derived state.

### 2.4 Unique And Composite Unique Constraints

MUST:

- Durable uniqueness invariants must use PostgreSQL unique constraints or unique indexes.
- Application pre-checks must not be treated as sufficient protection against duplicate races.
- Duplicate races must be handled from database constraint errors and mapped safely.
- Join tables representing unique pairings must use composite uniqueness.

SHOULD:

- Normalize values before storing and constraining identifiers where applicable.
- Prefer narrow unique constraints that match approved business invariants.

DOMAIN-SPECIFIC DECISION:

- Which product-domain fields are naturally unique, case-insensitive, or scoped by tenant/user/status.

### 2.5 Indexes

MUST:

- Unique constraints required for integrity must be explicit.
- Indexes that support FK enforcement, authorization checks, or common lookup paths must be reviewed during each domain feature.

SHOULD:

- Avoid speculative indexes without an expected query path.
- Prefer composite indexes that match real filter/sort order.

DOMAIN-SPECIFIC DECISION:

- Product-specific read-model and reporting indexes.

### 2.6 Timestamps

MUST:

- Mutable durable records define creation and update timestamps unless a feature explicitly documents why they are not useful.
- Immutable event-like records define creation timestamp and must not pretend to update historically immutable facts.

SHOULD:

- Use consistent names such as `createdAt` and `updatedAt`.
- Let repositories/services avoid client-controlled timestamp authority for server-owned records.

DOMAIN-SPECIFIC DECISION:

- Domain lifecycle timestamps such as submitted, settled, published, canceled, archived, or deleted timestamps.

### 2.7 Enum And Status Integrity

MUST:

- Status fields with a closed set of values must be constrained by Prisma enum, PostgreSQL enum/check constraint, or another approved database-level mechanism.
- Application validation must not be the only protection against invalid durable status values.

SHOULD:

- Keep status values canonical and uppercase or otherwise project-consistent.
- Keep transition rules in services/domain logic while the database constrains allowed values.

DOMAIN-SPECIFIC DECISION:

- The allowed status taxonomy and transition graph for each future domain.

### 2.8 Delete Policies

MUST:

- Every relation must choose and document one of: restrict/no-action, cascade, set-null, or an approved domain-specific policy.
- Restrict/no-action is the default for high-value or independently meaningful domain records.
- Cascade is allowed only for dependent records that have no independent lifecycle.
- Set-null is allowed only for optional historical references where preserving the child record without the parent is meaningful.

SHOULD:

- Prefer explicit service workflows for complex deletion/archival behavior.

DOMAIN-SPECIFIC DECISION:

- Soft delete, archive semantics, legal retention, and domain-specific cleanup workflows.

## 3. DB Constraints Vs Application Validation

Application validation is required for user-facing error quality and early rejection. It must not replace PostgreSQL constraints for durable invariants.

Required pattern:

- Request/schema validation rejects malformed client input.
- Services/repositories normalize approved values.
- PostgreSQL constraints enforce final integrity.
- Constraint errors are mapped to stable safe application errors.

Prohibited pattern:

- Relying only on pre-checks or Zod validation for uniqueness, FK existence, required fields, or closed status sets.

## 4. Concurrency And Integrity

Future domain features must treat concurrent writes as normal. Durable integrity must rely on:

- PostgreSQL unique/FK/NOT NULL constraints.
- FEAT-013 transaction runner for multi-write invariants.
- Safe handling of known Prisma/PostgreSQL constraint errors.
- Domain-specific locking, versioning, or idempotency only when the feature needs it.

Application pre-checks may improve UX but are not race protection.

## 5. Validation Strategy

FEAT-014 implementation must validate the standards without introducing product-domain schema.

Allowed validation approaches:

- Tests against existing approved identity/security schema constraints.
- Dedicated test-only fixtures/helpers that create and tear down temporary validation structures in isolated test databases without adding product-domain migrations.
- Static review/guard checks for prohibited schema patterns where practical.

Required live PostgreSQL evidence:

- UUID primary key behavior.
- `NOT NULL` rejection.
- unique constraint rejection.
- composite unique rejection.
- foreign key rejection.
- approved cascade/restrict/set-null behavior where existing schema or test fixtures can prove it.
- safe error mapping or non-leaky test output for constraint failures.

## 6. Migration Compatibility

FEAT-014 must follow FEAT-012 migration governance:

- Use `prisma migrate deploy`, `prisma migrate status`, and `prisma validate`.
- Use isolated test databases.
- Do not rely on developer-local `.env` for QA evidence.
- Do not use `db push` as migration governance.
- Do not introduce destructive migrations without explicit Human approval.
- Do not introduce Academy, Simulation, Community, Subscription, AI, or other concrete product-domain tables.

## 7. Prohibited Patterns

FEAT-014 must reject or document as invalid:

- New speculative product-domain tables.
- Global soft-delete convention.
- Destructive migration without Human approval.
- Application-validation-only durable invariants.
- Required domain fields stored nullable without approved rationale.
- Relationship fields without explicit FK/cardinality/deletion policy.
- Unique business invariants without database uniqueness.
- Client-controlled IDs/timestamps/roles treated as durable authority without explicit approval.
- Redis, JWT, client state, logs, or files acting as durable integrity authority.
- Raw SQL outside approved infrastructure, migrations, tests, or repository-owned code.

## 8. Exception And Approval Process

Any exception to a `MUST` rule requires:

- A feature-specific written rationale.
- Security/data-integrity risk assessment.
- Test coverage proving the alternative protects integrity.
- Explicit Human approval before implementation.

Any destructive/data-loss migration requires explicit Human approval before implementation or deployment.

Soft delete must be decided per later domain feature and is not approved globally by FEAT-014.

## 9. Regression Boundary

FEAT-014 must preserve:

- FEAT-002 identity persistence.
- FEAT-003 registration/password persistence.
- FEAT-004 login/access-token behavior.
- FEAT-005 refresh rotation/revocation.
- FEAT-006 logout invalidation.
- FEAT-007 RBAC.
- FEAT-008 admin guard.
- FEAT-009 auth audit semantics.
- FEAT-010A rate limiting.
- FEAT-011 persistence guard.
- FEAT-012 migration guard.
- FEAT-013 repository/transaction boundary.

## 11. Human Review Notes

FEAT-014 is a standards and validation feature. It gives later domain features a constraint baseline, but it does not decide their concrete schemas, soft-delete policies, or product workflows.
