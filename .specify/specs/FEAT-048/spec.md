# FEAT-048 Specification: Subscription Domain Schema & Persistence Foundation

Status: HUMAN MASTER PLANNING APPROVED / APPROVED FOR IMPLEMENTATION

## Data Contract

`UserSubscription` uses a server-generated UUID and required User FK. It stores `planKey`, `status`, `providerKey`, optional external subscription ID, `currentPeriodStart`, `currentPeriodEnd`, `cancelAtPeriodEnd`, optional trusted provider ordering marker, and timestamps. `ACTIVE` and `PAST_DUE` are non-terminal. `ACTIVE + cancelAtPeriodEnd=true` remains entitled only until valid `currentPeriodEnd`, then transitions to `EXPIRED`. `CANCELLED` is reserved for provider-confirmed immediate cancellation before normal period expiry. `CANCELLED` and `EXPIRED` are distinct terminal states and both deny premium.

`SubscriptionProviderEvent` stores provider/event identity, normalized type, occurred/received/processed timestamps, outcome, safe payload digest, allowlisted flat metadata, and optional subscription relation. It stores no raw payload.

`SubscriptionTransitionRecord` stores append-only before/after plan/status snapshots, operation source, actor/subject snapshots, request/correlation ID, transaction strategy, safe metadata, and occurrence time. It is product-domain history, not auth audit.

## Constraints

- UUID PKs and PostgreSQL FKs.
- Unique `(providerKey, providerEventId)`.
- Unique `(providerKey, externalSubscriptionId)` when external ID exists.
- Partial uniqueness enforcing one `ACTIVE`/`PAST_DUE` subscription per user.
- Closed plan/status/outcome/source/strategy values at database level where practical.
- Explicit indexes for current-user resolution, provider event lookup, external subscription lookup, and chronological transition history.
- RESTRICT/NO ACTION for User and meaningful subscription history; cascade only for strictly dependent records explicitly approved by the spec.

## Migration Contract

One additive FEAT-048 migration introduces all approved Phase 7 tables, enums, constraints, and indexes, including any dedicated subscription transition history approved under D6. It may not modify Phase 2-6 tables except adding an approved User relation generated by Prisma. No destructive SQL, `db push`, production seed, or migration-time premium grant is allowed.

Upgrade validation must begin at the exact `phase-6-approved` migration baseline, insert representative Identity, auth audit, Academy, Simulation, and Community rows, capture before state, apply FEAT-048, and prove preservation plus new constraints.

## Repository Contract

Approved interfaces cover subscription, provider-event, and transition-history repositories. The shared repository factory must create the same implementations for root and transaction clients. Controllers/services never import Prisma; FEAT-048 creates no controller and no provider-, command-, or reconciliation-originated transition service. A repository-level test harness may prove caller-owned UoW commit/rollback without taking transition ownership from FEAT-052/053.

## Security

No client input is authoritative. Diagnostics redact provider identifiers where sensitive, database URLs, SQL values, local paths, secrets, tokens, cookies, and payment data. `AuthSecurityAuditRecord` schema and taxonomy remain unchanged.
